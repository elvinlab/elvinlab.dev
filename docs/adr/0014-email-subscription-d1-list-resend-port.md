# 0014. Email subscription: the list lives in D1, the mail provider sits behind a port

Status: Accepted (issue #78, T50)

See also: the consolidated guide [`docs/SUBSCRIPTION.md`](../SUBSCRIPTION.md) ([English](../SUBSCRIPTION.en.md)).

## Context
RSS is the only way to follow the notes today. The owner wants visitors to subscribe by email and hear about each new note, with the list owned by the site so that changing the mail provider never means migrating subscribers. The site already has Cloudflare D1 (ADR 0013), the contact form with Turnstile, a rate limiter and a Resend adapter (ADR 0009).

## Decision
- **Source of truth: Cloudflare D1**, table `subscribers` in the site database (`SITE_DB`), migration `0002_subscribers.sql` (one numbered sequence for the whole database). Columns: `id` (random), `email` (unique, trimmed and lower-cased), `status` (`pending` | `confirmed` | `unsubscribed`), `locale`, `confirm_hash` and `confirm_expires` (single use, cleared on confirmation), `last_note` (slug of the last note sent to this subscriber), `created_at`, `confirmed_at`, `unsubscribed_at`.
- **Provider behind a port:** `SubscriberRepository` (D1 adapter) and `SubscriptionMailer` (Resend adapter) in `features/subscribe/ports.ts`, plus the same `verifier`, `limiter` and `now` ports as the contact form. The domain never imports a provider; a fake mailer in the tests proves that swapping the adapter needs no change to the domain or the schema.
- **Double opt-in:** subscribing stores `pending` and sends a confirmation link; only `confirmed` rows ever receive a note. The confirmation token is 32 random bytes, only its SHA-256 hash is stored, it expires in 48 hours and it is cleared on use (single use). The link opens a page with a button, and the button POSTs: a mail scanner that prefetches links must not confirm anyone.
- **Unsubscribe is ours:** a stateless link `token = id.HMAC(SUBSCRIBE_TOKEN_SECRET, id)`. It needs no per-subscriber token in the database (a stored hash could not be put back into later emails), works without login, is idempotent and flips the D1 row, so D1 always knows who left whichever provider sends. Every note email carries it as a link in the body and as the `List-Unsubscribe` header, both pointing at the human page (no RFC 8058 one-click POST, see Consequences). The page shows a button that POSTs, so a mail scanner that prefetches the link unsubscribes nobody.
- **No leak, no duplicates:** subscribing the same address again answers the same generic success. A `pending` row gets a fresh confirmation after a cooldown, a `confirmed` row is left alone, an `unsubscribed` row goes back to `pending`. Stale `pending` rows (over 7 days) are purged lazily on each subscription.
- **Abuse:** Turnstile (action `subscribe`), honeypot, minimum fill time and a rate limiter binding `SUBSCRIBE_RATE_LIMITER`, as in ADR 0009. Fail closed: with no bindings the Action answers `SERVICE_UNAVAILABLE` and no form renders. Logs carry stage names and codes only, never an address or a token.
- **Behind a flag, off by default:** `features.subscribe`. The owner enables it after the human steps (apply the migration remotely, set the secrets `SUBSCRIBE_FROM` and `SUBSCRIBE_TOKEN_SECRET`, bind the rate limiter), listed in `docs/CONFIGURATION.md`.

### Sending a new note: our own list through the normal API, not Resend broadcasts
Options considered:
- **(a) Sync confirmed rows into a Resend audience and send a Broadcast.** No daily cap on broadcasts as far as the pricing page says (free: 1,000 marketing contacts), but the list would live in two places. Resend's own unsubscribe would have to be mirrored back into D1 by a webhook, and the documentation I could read does not confirm that event; the free plan's inclusion of broadcasts is not stated either. A mismatch means mailing someone who unsubscribed, which is the failure this design exists to prevent.
- **(b) Send from our own list with the batch API.** Resend sends up to 100 emails per batch call, accepts custom headers (the `List-Unsubscribe` pair) and an `Idempotency-Key`. The free plan allows 3,000 emails a month and 100 a day (https://resend.com/pricing.md, https://resend.com/docs/api-reference/emails/send-batch-emails, read 2026-10-05).

**Chosen: (b).** D1 stays the only source of truth, the unsubscribe is ours and instant, and nothing depends on an unconfirmed webhook. The cost is the 100-a-day cap: a note reaches at most 100 subscribers per day on the free plan. The sender is therefore resumable: `last_note` records who already got which note, so a second run the next day continues where the first stopped, and an idempotency key per note, subscriber group and day prevents double sends. A paid Resend plan lifts the cap without changing the code.
- **Manual trigger at first.** This task delivers the sending core (domain function, batch adapter, tests with a fake). Running it after publishing a note is an owner step; an owner-run command or a protected endpoint is a follow-up.

## Consequences
- **One-click unsubscribe (RFC 8058) was dropped.** A mail client's one-click POST is a form-type request without an `Origin` header, which Astro's `security.checkOrigin` rejects with 403 (observed on the fixture preview); turning that check off would weaken every endpoint of the site. The `List-Unsubscribe` header therefore carries the unsubscribe page URL and `List-Unsubscribe-Post` is not sent. Revisit if sending volume ever makes one-click mandatory under bulk-sender rules.
- The site now stores personal data (an email address, its status and dates). `/privacy` gains a section: what is kept, why, Resend as the processor, the unsubscribe link in every email, and deletion on request through `/contact`. A row marked `unsubscribed` is kept as a suppression entry until deletion is requested, so a re-import can never re-add the address.
- A new D1 migration and two secrets are owner operations in Cloudflare; the code never touches them (`docs/CONFIGURATION.md`).
- The 100-a-day free cap bounds how fast a note spreads; at the current audience it is not a constraint, and it is documented for when it is.
- The contact feature's Turnstile adapter hard-codes the action `contact`; it becomes a parameter so both features share one verifier implementation.

## Update 2026-10-05: one form, in the footer; consent covers project announcements
- **The form lives only in the global footer band** (`shared/subscribe/SubscribeBand.astro`). The notes sidebar card and the link at the foot of each note are gone, and the band no longer hides on `/notes/`. It still hides on `/subscribe/*`, the printable `/me`, and when the flag, the blog or a Turnstile key is missing.
- **Why the page stays light:** the footer is on every page and the LCP gate has little margin. The band ships markup plus a few-line stub; on the first `focusin` or `pointerenter` on the form the stub `import()`s the form module (`shared/subscribe/form-client.ts`), which loads Turnstile with `appearance: 'interaction-only'` (no layout shift) and calls the Action by plain `fetch`. A submit that races the import is held and replayed. Nothing loads, and Turnstile is never requested, for a visitor who does not touch the form. The server side (domain, adapters, Actions) stays in `features/subscribe/`; the client reads policy only through `shared/subscribe/client-policy.ts` and `data-*` attributes.
- **Consent now covers the notes and occasional announcements of the owner's own projects**, stated in the band, the confirmation email, the confirm and unsubscribe pages and the `/privacy` section, so the list can announce a project later without asking again. Nothing else is promised and the address is never shared.

## Update 2026-10-06: designed HTML emails plus a plain-text part
- **Both messages (confirmation and new note) are now sent as `html` plus `text`** by the Resend adapter, rendered by pure functions in `features/subscribe/email-templates.ts` (no Astro, no provider imports). The mailer port is unchanged; the adapter config gains the site URL, site name and owner name, so no owner string is hard-coded in the template.
- **Table layout, inline CSS, system fonts.** Email clients strip or ignore `<style>`, web fonts and most modern CSS, so the layout is a 600 px `role="presentation"` table with inline styles, a bulletproof button and system font stacks (monospace for the wordmark). Press Start 2P and Space Grotesk are deliberately not used; the pixel identity comes from the logo, the dashed borders and one pink bar.
- **Light by default, dark as an override.** Gmail ignores `prefers-color-scheme`, so the light design is the safe baseline; a small `<style>` block (dark override and a mobile padding rule) only enhances it and everything stays correct when it is stripped.
- **Logo hosted at `/email/logo.png`** (64x64, generated from `favicon.svg`, shown at 32x32) and referenced by an absolute URL built from the site URL; with images blocked the wordmark text carries the brand. No tracking pixel, remote CSS, remote fonts or script. Every dynamic value is HTML-escaped; link URLs and token handling are unchanged.
- Preview without sending: `docs/TESTING.md`, section "Email previews".

## Update 2026-10-06: global cap on confirmation emails and the shared daily pool
- **Why:** Resend's free plan allows 100 emails a day in total, shared by confirmation emails and note emails. A distributed attack (many IPs, each under the per-IP limit) could burn that pool with confirmation requests and leave nothing for notes.
- **Decision (owner): at most 30 confirmation emails per UTC day** (`SUBSCRIBE_POLICY.confirmationsDailyCap`), out of `providerDailyTotal` = 100. The count lives in D1, table `subscribe_quota (day, confirmations)`, created by the same migration `0002_subscribers.sql` (not yet applied to any remote database, so no 0003). One atomic statement (`INSERT ... ON CONFLICT DO UPDATE ... WHERE confirmations < cap RETURNING`) reserves a slot, so concurrent requests cannot overshoot.
- **Where it applies:** right before every confirmation mail (new address, pending address past the cooldown, unsubscribed address coming back), after the other gates and before the mailer call. A slot is consumed even if the send fails, and a `confirmed` address or a pending one inside the cooldown consumes nothing. Once the day is at the cap, every address gets the same fixed public result (`daily_cap`, mapped to a `TOO_MANY_REQUESTS` Action error with a fixed message), so it never reveals whether an address exists. Reports carry the stage name only.
- **Notes use what is left:** `sendNote` sends at most `providerDailyTotal - confirmationsToday` emails per run (never above the per-run cap of 100); with nothing left it returns `sent: 0` without calling the mailer, and the next day resumes through `last_note`.

## Update 2026-10-06: the owner trigger for sending a note
- **Problem:** `sendNote` existed and was tested with fakes, but nothing could call it, so no note could reach the list.
- **Decision: a protected endpoint plus a command.** `POST /api/subscribe/notify` is a server route (`prerender = false`) injected by the same flag-gated integration as the confirmation pages, so it does not exist when `features.subscribe` or the blog is off (the white-label build asserts it). The owner runs `pnpm notify:note <slug> [--send]`, which calls it. An endpoint (instead of a local script talking to D1) reuses the Worker's own bindings, so no Cloudflare or Resend credential ever sits on the owner's machine; the command needs only one secret.
- **Auth:** a Bearer token compared in constant time (both values are hashed with SHA-256 and compared byte by byte) with the new secret `SUBSCRIBE_ADMIN_TOKEN` (at least 32 characters). The existing `SUBSCRIBE_RATE_LIMITER` binding is reused with the key `notify:<ip>` and is checked before the token, so guessing is throttled whether or not a guess is right. A wrong or missing token answers a bare 401 and only the stage name `notify_auth` is logged; a missing or short secret answers 503. The secret is validated by its own schema (`notifyBindingsSchema`), not by the public subscribe schema, so a site that has not created it yet keeps its subscription working. The request must be `application/json`, which keeps it compatible with `security.checkOrigin`, which stays on.
- **The owner sends only a slug.** The body is `{ slug, dryRun? }` (strict, at most 1 KiB). Title, summary and link are built server side from the published note, and the link follows the note's language, so a leaked token can never put arbitrary text in front of the list. An unknown slug answers 404 after authentication.
- **Language rule:** a note reaches only the confirmed subscribers whose locale equals the note's language (`listUnnotified` and `countUnnotified` take the locale and bind it). The email copy language stays the recipient's locale, which is now also the note's.
- **Dry run by default.** The command sends nothing unless `--send` is given. A dry run calls no mailer and writes nothing; it returns `{ recipients, wouldSend, remainingPool }` from the same selection and the shared daily pool. A real send returns `{ sent, remaining, failed }` and nothing else: no address or token ever appears in a response, a report line or the command output. The cap (batches of at most 100, resume through `last_note`, one idempotency key per batch, the pool shared with confirmations) is unchanged; when `remaining > 0` the command says to run it again the next day.
- **Operational note:** the token is read only from the environment variable `SUBSCRIBE_ADMIN_TOKEN`, never from a file or an argument, and the command refuses a non-https site URL so it never travels in clear text.

## Update 2026-10-06: a delivery ledger replaces `last_note` as the send rule
- **Problem (found in production):** `subscribers.last_note` held one slug per subscriber and recipients were `last_note IS NULL OR last_note <> slug`. After sending note 1, note 3 (sent earlier) looked "not received" again, so re-running it, or sending older notes out of order, would have mailed the same people twice.
- **Decision:** a table `subscriber_notes (subscriber_id, slug, sent_at)` with primary key `(subscriber_id, slug)` and `ON DELETE CASCADE`, created by migration `0003_subscriber_notes.sql` (0002 was already applied remotely, so it was not edited). A confirmed subscriber of the note's language is a recipient only when no row exists for that slug. `markNotified(ids, slug, now)` inserts the rows with `INSERT OR IGNORE ... SELECT value FROM json_each(?1)` (ids travel as one JSON array because D1 caps bound parameters at 100 per statement) and still writes `last_note`, which stays as an informational "last send" and decides nothing. Batches of at most 100, the shared daily pool, the idempotency key, "mark only after the mailer succeeded" and resumability are unchanged.
- **Why not widen `last_note`:** one column cannot remember several notes; a table makes a duplicate impossible by construction, whatever the order or the number of re-runs.
- **Privacy:** the table is personal data (which notes a person was sent), so `/privacy` says so, and deletion removes it with the subscriber (explicit delete first, cascade as a backstop).
- **Backfill and one-off fix:** the migration copies each subscriber's `last_note` (note 1 in production). Before it existed, note 3 was sent first, and then note 1, so the ledger only knows note 1. After applying 0003 remotely, the owner records note 3 once (do not run it before 0003 is applied):

```sql
INSERT OR IGNORE INTO subscriber_notes (subscriber_id, slug, sent_at) SELECT id, 'vibe-coding-o-especificar-primero', COALESCE(confirmed_at, created_at, 0) FROM subscribers WHERE status IN ('confirmed','unsubscribed');
```
